# Unitree J288 / S288 ID 配置

独立窗口入口：其他工具 → Unitree J288 / S288 → 舵机设置。

串口固定为 6,000,000 bps、8N1、无流控。先只连接一台已上电舵机，
扫描并选择现有 ID，停止运动，再输入不同的新 ID（0–14），点击
「修改 ID 并保存到舵机」。成功后自动选中新 ID，并更新本机配置。
「保存到本机」保存电脑上的运动与通信参数；上述 ID 按钮才写入舵机 Flash。

## 协议来源与核对方法

- 用户提供的 `电机调试使用手册.pdf` 说明了修改 ID、恢复 APP 和引导操作。
- `digital_servo-1.0.1` 的公开例程只设置运动报文的目标 ID，不包含 Flash 配置事务。
- 实现依据为官方 [Unitree-Motor-Assistant](https://github.com/unitreerobotics/Unitree-Motor-Assistant)
  中随 J288 / S288 Qt 助手分发的 `libUnitreeMotorSDK.dll`，
  [V1.2.0 分发版本](https://github.com/unitreerobotics/Unitree-Motor-Assistant/blob/1267299be480/Unitree%20Motor%20Assistant.exe)。
  此仓库明确支持 J288 / S288；另一个 Electron
  [unitree-motor-debugging-assistant](https://github.com/unitreerobotics/unitree-motor-debugging-assistant)
  面向 GO-M8010-6。
- 官方助手样本 SHA-256：
  `3b8f2eddcca81ef9a8f6bd60c68203ab8d15565cebbe429129783c3590f620cc`。
- 核对 SDK 导出 `Change_ID_Safe`、内部 ID 写入/保存事务、J288 模式映射、
  构帧和应答解析函数。另用隔离的 x86-64 CPU 仿真执行原构帧函数，
  取得六组逐字节测试向量；四组应答也通过同一 SDK 的原解析函数验证。
  构帧函数 RVA 为 `0x23380`，应答解析 RVA 为 `0x231e0`，
  ID 事务 RVA 为 `0x277c0`，均相对该 SDK 的映像基址。
- 工程独立用 Rust 实现协议，不分发或运行官方 Windows DLL，也不依赖 Wine 或仿真库。

下列字段是从 SDK 实现恢复的协议行为，不是厂商公开的完整配置协议规范。

## 配置事务

1. 检查新 ID 是否已有 APP 应答；串口异常不能当作 ID 空闲。
2. 从旧 ID 获取新的锁定模式反馈，确认无故障。
3. 给旧 ID 发普通 20 字节运动帧，模式字段设为 **7**，其余目标归零；等待 100 ms。
   这里是引导切换，不是 FOC。SDK 的引导过渡帧允许无应答；后续握手必须成功。
4. Boot 读：旧 ID、长度码 8、命令 0、扇区 0、地址 `0x20`，取得 16 字节挑战值。
5. Boot 写：旧 ID、长度码 8、命令 1、扇区 0、地址 `0x10`，原样回写挑战值，解锁参数存储。
6. Boot 写：旧 ID、长度码 0、命令 1、扇区 0、地址 `4`，8 字节数据首字节为新 ID，其余为零。
   应答仍应匹配旧 ID，且数据首字节必须回显新 ID。
7. **Boot 保存**：新 ID、长度码 0、命令 **2**、扇区 0、地址 `0`。
   SDK 在 8 字节数据中携带客户端标记及秒时间戳；本工程使用
   `19 68 65 78`（`0x19` 前缀及 `hex` 标记）和小端 Unix 秒时间戳。
   等待匹配且成功的应答，最多 3 s，收到前不标记「已保存」。
8. Boot 读：新 ID、长度码 0、命令 0、扇区 0、地址 `4`，检查 ID 回读。
9. **恢复 APP**：新 ID、长度码 0、命令 **5**、扇区 0、地址 `0`。
   然后用新 ID 的普通模式 0 帧确认 APP 已运行并锁定。

成功要求保存应答、ID 回读和新 ID 的 APP 锁定反馈都成立。
程序不会通过重新连接或仅修改通信目标，宣称舵机存储的 ID 已改变。

目的地址占用检查只能发现有正常应答的设备；重复 ID、断电设备和接线异常无法可靠识别，
因此 ID 配置时仅连接一台舵机。

## 报文字节

Boot 请求（数据长度 N = 8 或 16）：

| 偏移 | 内容 |
| --- | --- |
| 0–1 | `FE EE` |
| 2 | `ID \| F0` |
| 3 | `00` |
| 4 | `ID \| F0` |
| 5 | 高 4 位长度码，低 4 位命令 |
| 6–7 | 小端 14 位地址；高 2 位为扇区，本功能固定 0 |
| 8 起 | N 字节数据 |
| 8+N 起 | 小端 CRC32，覆盖此前全部字节 |

长度码 **0 表示固定 8 字节**，不是 0 字节；长度码 **8 表示 16 字节**。
请求总长为 20 或 28 字节；相应应答总长为 **26 或 34 字节**。

Boot 应答以 `FC EE` 开头。偏移 2 低 4 位为 ID、最高位为成功状态；
偏移 3 为长度码和命令；4–5 为地址和扇区；数据从 **偏移 6** 开始。
末尾 4 字节 CRC 覆盖偏移 2 到 CRC 前的字节，包含数据后的 8 字节附加区域。
应答必须匹配 ID、长度码、命令、地址和扇区，且成功位为 1。

CRC 与运动协议相同：初值 `FFFFFFFF`，多项式 `04C11DB7`，
逐小端 u32、最高位优先，不做最终异或。

旧 ID 0 写新 ID 3 的请求：

```text
FE EE F0 00 F0 01 04 00 03 00 00 00 00 00 00 00 C0 FB 66 FB
```

新 ID 3 保存请求，测试用客户端标记 `19 AB CD EF`、时间戳 `0x12345678`：

```text
FE EE F3 00 F3 02 00 00 19 AB CD EF 78 56 34 12 A6 70 FA E3
```

其余官方构帧向量和通过官方解析器的应答向量见
`src-tauri/src/unitree_boot.rs` 的测试。

## 异常和生命周期

串口由一个工作线程独占。进入 Boot 后，普通监控、扫描、运动及其他配置不会插入事务。
操作前必须停机。Flash 保存期间的 Stop 请求排队到事务及 APP 恢复结束后处理；
全程不发送 FOC。IPC 使用现有生命周期锁和持久设置门禁，断开连接会等待，
原生关闭在配置期间会暂缓。

写入或保存结果不明时不会自动重写或重复保存。程序尝试在可能的新、旧地址恢复 APP，
分别保留「已发送 ID 写入」「已收到保存应答」和错误信息。
即使新 ID 已能通信，保存应答丢失时也明确标记断电保持尚未确认。
没有恢复 APP 时停止常规轮询并禁用运动，可在设备设置中指定 ID 再试「恢复 APP」。

## 验证范围

```sh
cargo test --offline --manifest-path src-tauri/Cargo.toml --example unitree_probe
npm test
npx tsc --noEmit
npm run build
cargo build --offline --manifest-path src-tauri/Cargo.toml
```

测试覆盖官方构帧/解析向量、应答分片及 TX 回显、ID 冲突、非法和过期目标、
解锁拒绝、ID 回显不符、CRC 错误、保存应答丢失/错误/拒绝、回读不符、
APP 跳转应答丢失、保存期间 Stop、独立的易失/持久 ID 状态。

协议和自动化测试不能代替已上电 J288 / S288 的实际写入及断电重启验证。
官方 SDK 恢复的配置流程，包括保存元数据的固件兼容性，仍需实机确认。
`unitree_probe` 命令只逐个发送锁定模式查询，不修改 ID、不保存 Flash、不进入 FOC。
